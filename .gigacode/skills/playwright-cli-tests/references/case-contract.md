# Контракт тест-кейса и результата

Используй формат проекта, если он сохраняет перечисленные сведения. Описание и результаты прогона храни отдельно: наблюдаемое поведение не изменяет ожидаемое.

## Карточка кейса

```markdown
# TC-<ID>: <проверяемое поведение>

- Состояние описания: draft | ready
- Происхождение: extracted | designed
- Источник: URL/файл, исходный ID, раздел/требование
- Доступ к источнику: профиль jira/wiki и env-имена его URL/логина/пароля; отдельно от профиля приложения
- Источник прочитан: дата; версия документа, если доступна
- Цель: что проверяем
- Приоритет: из источника или обоснованный при проектировании
- Стенд: устойчивое имя стенда (например stage), URL из конкретной env-переменной
- Продукт: устойчивое имя продукта/модуля (например news), ограничения версии/браузера
- Учётная запись: роль и точные env-имена для логина и пароля (или явно anonymous/SSO)
- Предусловия: начальное состояние, способ подготовки
- Данные: соответствие полей именам env-переменных, типы/ограничения и ссылки на fixtures, без значений секретов

| Шаг | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | Конкретное действие с данными | Наблюдаемая и проверяемая реакция |

- Постусловия и очистка: какие собственные данные удалить/восстановить
- Варианты: отличающиеся данные и ожидания, если применимо
- Открытые вопросы/предположения: явно перечислить, либо «нет»
- Автоматизация: ready | blocked | manual-only; причина
```

`ready` означает достаточную определённость требований, не успешный прогон. `manual-only` требует конкретной причины, например физического действия вне доступных инструментов; сам факт отсутствия автотеста не подходит. Неготовый доступ к стенду блокирует исполнение, но не обязательно готовность описания.

Сохраняй ID источника. Если его нет, назначь устойчивый локальный ID; при следующих чтениях переиспользуй его. Вариантам давай различимые суффиксы. Не добавляй ожидаемые сообщения/правила в извлечённый кейс без источника. Локаторы и технические заметки исследования храни отдельно от бизнес-ожиданий.

## Тестовые данные через env

### Создание профиля по .env перед выполнением

Перед чтением защищённого источника проверь `config/sources.json`, перед прогоном кейса или исследовательской сессией — выбранный профиль в `config/profiles.json`. Если нужного профиля нет или файл пуст, создай его по локальному `.env`, именам переменных окружения и однозначному контексту кейса/проекта. Это действие выполняет агент; `init` сам соответствия не определяет.

1. Используй парсер env проекта или Node.js `util.parseEnv`, без исполнения `.env` через shell. Для сопоставления извлекай только имена переменных и признаки наличия значений; не печатай содержимое `.env`, пароли, токены или их значения в чат и логи. При проверке учитывай приоритет окружения процесса над `.env`.
2. Определи стенд, продукт и роль по именам переменных и заданному контексту. Например, `STAGE_SHOP_EDITOR_URL`, `STAGE_SHOP_EDITOR_LOGIN`, `STAGE_SHOP_EDITOR_PASSWORD` позволяют описать stage/shop/editor. Имена `URL`, `USER`, `PASS` сами по себе не определяют стенд или продукт. Не выводи назначение учётной записи из значения пароля.
3. Добавь только нужный отсутствующий профиль: `stand`, `product`, `role`, явно определённый `auth` и `env` с привязками `baseURL`, `login`, `password` к точным именам переменных. Для явно анонимного доступа используй `auth: "anonymous"` без выдуманных кредов. В конфигурацию записывай имена переменных, а не их значения.
4. Сохрани все существующие профили, поля и привязки. При конфликте с выбранным профилем не перезаписывай его автоматически. Если неоднозначны назначение переменных, стенд, продукт, роль или способ авторизации, уточни только недостающие сведения. Не проверяй догадки попытками входа. Отсутствие обязательного значения блокирует зависимое действие.
5. Доступы Jira/Wiki сопоставляй отдельно в `config/sources.json` (`auth` и `env`), с проверкой origin перед передачей кредов. Если кейс ещё недоступен, используй контекст источника для его профиля; профиль приложения определи после чтения кейса. Учётные данные источника не назначай приложению.
6. Запиши выбранное имя профиля в карточку кейса или план исследования, проверь обязательные env-привязки средствами runtime и продолжи workflow без дополнительного подтверждения, если соответствие однозначно. Не изменяй `.env` и не создавай фиктивные значения ради прохождения проверки.

Карточка должна однозначно определять связку `стенд + продукт + роль → URL, логин, пароль`. Для каждого поля укажи точное имя env-переменной; общие `TEST_USER_EMAIL`/`TEST_USER_PASSWORD` недостаточны, если в окружении несколько продуктов или стендов. Переиспользуй явные имена проекта. Для новых переменных используй префикс стенда и продукта, для учётных данных также роль, например:

```markdown
## Контекст выполнения

- Стенд: stage
- Продукт: news
- Роль: editor
- URL приложения: env STAGE_NEWS_BASE_URL
- Логин: env STAGE_NEWS_EDITOR_LOGIN
- Пароль: env STAGE_NEWS_EDITOR_PASSWORD
- Данные поиска: env STAGE_NEWS_SEARCH_QUERY
```

Это пример привязки, а не значения по умолчанию. Извлекай стенд/продукт/роль из кейса или явно заданного контекста запроса и сохраняй выбранную привязку в карточке до выполнения. Если разрешено несколько стендов, перечисли отдельные именованные профили с точными env-именами и выбери профиль по запросу. При единственном однозначном профиле используй его. При нескольких без выбора или конфликте кейса и запроса уточни профиль, не запускай тест на случайном стенде. Если имена переменных ещё не определены, задай согласованную схему в карточке и `.env.example`; отсутствие заполненных значений блокирует исполнение.

Не перебирай логины/пароли и не подбирай их по похожим именам. Не переключайся на другой продукт, стенд или роль после ошибки авторизации. Проверь полную выбранную связку перед первым действием. URL страницы с документацией/кейсом — источник требований, он не определяет стенд приложения. Для anonymous или SSO явно укажи режим и необходимые env-ссылки, не требуй фиктивный пароль.

В автотесте сохрани привязку ID кейса к профилю и точным env-именам через конфигурацию/fixtures. В Markdown-отчёте повтори фактически выбранные стенд, продукт, роль и имена переменных URL/логина/пароля; значения учётных данных не выводи. Не сообщай, что профиль проверен, если его переменные не были разрешены и использованы.

Все входные тестовые данные передавай через переменные окружения: адрес стенда, учётные данные, роли, значения форм, поисковые запросы, идентификаторы и параметры вариантов. Не зашивай их в spec, fixtures, команды или карточки кейсов. Сохраняй в Markdown соответствие, например `поле логина ← TEST_USER_EMAIL`, `поиск ← TEST_SEARCH_QUERY`. Это обозначение источника значения, а не строка для ввода в браузере. Фиксированные бизнес-ожидания по требованиям не заменяй автоматически входными данными или наблюдаемым результатом.

- Источники: окружение процесса/CI либо локальный `.env`. Явно загружай `.env` поддерживаемым проектом загрузчиком до чтения конфигурации/fixtures; не предполагай автоматическую загрузку и не исполняй файл как shell-скрипт. Уже переданные переменные окружения имеют приоритет над `.env`.
- До первого действия проверь наличие и типы переменных, необходимых выбранным кейсам. Не требуй данные для несвязанных сценариев. Отсутствующую переменную отличай от заданной пустой строки: пустота может быть входом негативного кейса. Не изменяй пробелы в паролях и вводимых строках. Числа, boolean и JSON преобразуй и проверяй явно.
- Если необходимых данных нет или формат неверен, останови затронутый кейс до изменения состояния и запиши `blocked` с именами переменных, без их значений. Не используй выдуманные или захардкоженные запасные значения.
- Для значений из исходного кейса сохрани соответствие env-именам. Несекретные исходные значения можно перенести в локальный `.env` в рамках подготовки данных, не перезаписывая существующие; секреты пользователь/CI передаёт через предусмотренный защищённый канал. Пробелы в данных не заполняй догадками.
- Уникальные данные допускается производить из env-параметров/seed и ID запуска в fixtures. Зафиксируй правило генерации; созданные приложением ID и результаты операций остаются runtime-данными, их не нужно записывать обратно в `.env`.
- Поддерживай `.env.example` с именами, назначением и безопасными пустыми значениями. Исключай реальные `.env` и файлы секретов из git. Не печатай окружение целиком, секреты или их значения в командах, названиях тестов, отчётах и логах. Скриншоты и trace также учитывай как потенциальные носители секретов.
- MCP не обязан раскрывать окружение агента или автоматически подставлять `$VAR`. Получай значения доступным разрешённым способом на стороне клиента/процесса и передавай фактические значения полям инструмента только при выполнении. Предпочитай механизм секретов/маскирования клиента; если безопасная передача секрета недоступна, отметь блокер. Не отправляй строку `TEST_USER_PASSWORD` или `${TEST_USER_PASSWORD}` как пароль и не считывай env через JavaScript страницы.

## Отчёт прогона

### Доступ к Jira/Wiki и ошибки сертификата

Для чтения источников используй отдельные профили: `jira` → `JIRA_BASE_URL`, `JIRA_LOGIN`, `JIRA_PASSWORD`; `wiki` → `WIKI_BASE_URL`, `WIKI_LOGIN`, `WIKI_PASSWORD`. В текущем проекте привязки хранятся в `config/sources.json`, профили тестируемых продуктов — в `config/profiles.json`. Не используй пароль продукта для Jira/Wiki и не пробуй чужие профили после ошибки входа. Сравни origin полученной ссылки с URL источника до передачи учётных данных. Для SSO/MFA нужен предусмотренный для конкретного сайта процесс; автоматический подбор логина или обход MFA не допускается.

По требованию пользователя ошибки SSL/TLS игнорируются для всех сайтов в тестовых браузерах: Jira, Wiki, продукты, ресурсы и редиректы. Runtime и Playwright Test используют `ignoreHTTPSErrors: true` во всех создаваемых контекстах; CLI — `.playwright/cli.config.json`, MCP — `--ignore-https-errors` в конфигурации запуска. Отдельные env-флаги и разрешения по сайтам не нужны. Это настройка браузерной автоматизации; `NODE_TLS_REJECT_UNAUTHORIZED=0` не требуется. Учётные данные по-прежнему выбираются по профилю, origin источника проверяется перед передачей пароля.

Если уже открытая MCP-сессия показывает предупреждение, по актуальному snapshot нажми видимое «Дополнительные параметры»/«Advanced», затем «Перейти на сайт»/«Proceed». Не запрашивай отдельное подтверждение для каждого сайта. Если кнопки нет, пересоздай собственную сессию с параметром игнорирования ошибок сертификата; при невозможности укажи блокер. Не угадывай refs и не применяй скрытые клавиатурные обходы. Запиши фактический TLS-режим в отчёт. Новые настройки MCP/CLI применяются после перезапуска их сессий.

После каждого прогона сохраняй обязательный Markdown-отчёт, в том числе при падении, блокировке или прерывании. Записывай результаты по мере выполнения, чтобы уже пройденные шаги не потерялись. HTML/trace и сообщение в чате могут дополнять, но не заменять `.md`.

В шапке: run ID, дата/время и часовой пояс, режим MCP/automation, стенд, браузер, роль без секретов, версия приложения/commit при наличии, выбранные кейсы и фактический охват источников.

| ID / вариант | Шаг или spec/test | Ожидание | Факт | Статус | Доказательство |
| --- | --- | --- | --- | --- | --- |

- `passed`: проверка выполнена, факт соответствует ожиданию. Весь кейс passed только при выполнении всех обязательных проверок.
- `failed`: обнаружено подтверждённое расхождение с определённым ожиданием.
- `blocked`: проверку нельзя выполнить из-за доступа, среды, данных или неопределённых требований; укажи причину.
- `not_run`: проверка не запускалась, например после провала зависимого шага или вне выбранного объёма.

Для automation дополнительно сохраняй исходные статусы runner, включая skipped/flaky/timedOut/interrupted, число попыток и код выхода. Не превращай skipped или flaky в passed. Если кейс состоит из нескольких тестов, покажи все результаты перед общим выводом.

Для дефекта: ID кейса, воспроизводимые шаги, ожидание, факт, доказательство, влияние; не публикуй внешнюю задачу без запроса. Для повторного прогона сохрани связь с предыдущим run ID и причину. Для cleanup отдельно укажи результат и оставшиеся данные. Итоги должны учитывать каждый выбранный кейс, в том числе заблокированные и не запущенные.

## Шаги и скриншоты в Markdown

Помимо итоговой таблицы, для каждого шага кейса добавляй отдельный раздел: действие, ожидаемый результат, фактический результат, статус и скриншот. Показывай также не выполненные шаги с причиной, без выдуманных фактов или изображений.

Снимай скриншот после проверки каждого выполненного UI-шага, включая успешные. При ошибке снимай текущее состояние до cleanup, закрытия страницы и повторного запуска. Скриншот дополняет проверку ожидания, а не заменяет assertion. Для шага без UI укажи «скриншот неприменим» и приложи фактическое доказательство. Если снимок недоступен (например, браузер упал), укажи причину и отметь неполноту доказательств; ошибка снимка не должна скрывать исходную ошибку теста.

Markdown отображает отдельные файлы изображений через `![описание](относительный/путь.png)`. Сохраняй их в постоянной папке рядом с отчётом, не ссылайся на временные файлы MCP/runner. По умолчанию:

```text
reports/manual/<run-id>.md          # либо reports/automation/<run-id>.md
reports/manual/<run-id>/screenshots/TC-12-chromium-attempt-1-step-01.png
```

Для automation используй ту же структуру внутри `reports/automation/`. Имена должны различать кейс, вариант, проект/браузер, попытку и шаг; параллельные запуски не должны перезаписывать файлы. Сохраняй каждую попытку отдельно. При передаче отчёта передавай `.md` вместе с его папкой изображений.

Пример одного раздела (иллюстрация формата, не результат реального прогона):

```markdown
## TC-12 — chromium — попытка 1

### Шаг 1. Открыть страницу входа

- Действие: перейти на страницу входа тестового стенда.
- Ожидание: видны поля логина и пароля и кнопка «Войти».
- Факт: оба поля и кнопка отображаются.
- Статус: passed.

![TC-12, шаг 1: форма входа](run-001/screenshots/TC-12-chromium-attempt-1-step-01.png)
```

Перед завершением проверь, что все ссылки на изображения разрешаются относительно `.md`, файлы существуют и открываются как изображения, а каждый выполненный UI-шаг содержит скриншот либо явную причину его отсутствия. Не включай секреты и лишние персональные данные: маскируй чувствительные области при захвате; если безопасный снимок невозможен, запиши это как ограничение доказательств. Не вставляй base64 вместо обычных ссылок: его отображение в Markdown-просмотрщиках не гарантировано.

## Отдельный баг-репорт

При обнаружении дефекта обязательно сохрани отдельный Markdown-файл с заголовком, ID кейса/эксперимента, источником требований, стендом/продуктом/ролью, предусловиями и env-привязками, шагами воспроизведения, ожиданием и фактом, влиянием/серьёзностью, результатом повторной проверки и скриншотами. Добавь ссылку на него в отчёт прогона. Не публикуй задачу в Jira без отдельного запроса.

Падение автотеста само по себе не доказывает баг продукта. Runtime автоматически создаёт черновик `reports/<mode>/<run-id>/bugs/BUG-<id>.md` для упавшего шага; blocked и успешные кейсы не становятся багами. Агент разбирает причину и классифицирует её как product/test/environment/requirements/unknown. Для product нужны обоснование, влияние и фактический результат повторной проверки (допустимо явно «не повторялось»). После подтверждения обнови тот же `.md`, сохранив исходные доказательства. Повторы разных попыток имеют отдельные файлы; не выдавай retry за новый независимый дефект.

Для автоматизации после завершения прогона сохрани assessment JSON и вызови `npx --no-install playwright-qa bug reports/automation/<run-id>/summary.json evidence/assessment.json`. Поля: `id`, `browser`, `attempt`, `kind`, `reason`, а для product также `impact`, `reproduction`; дополнительно `title`, `severity`, `preconditions`. Формат описан в [runtime-api.md](runtime-api.md). Для MCP/исследования можно включить тот же объект в `record.defect` журнала и вызвать `qa report`; либо сохранить баг-репорт самостоятельно по указанной структуре. Никакие пароли или значения секретных env-переменных не должны попадать в файл.
