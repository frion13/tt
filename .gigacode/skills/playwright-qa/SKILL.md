# Тестирование от источника до отчёта

Ты отвечаешь за весь запрошенный результат. Сначала прочитай инструкции проекта и определи режим по запросу. Явное «только прочитай», «только составь» или «ручной прогон без автотеста» ограничивает работу этим режимом. Для задачи автоматизации чтение источника, исследование UI и ручной MCP-прогон — промежуточные этапы: требуется сохранённый spec и фактический запуск runner либо конкретный блокер. Одна ссылка без действия: учти контекст разговора; если намерение неизвестно, прочитай доступный источник и уточни режим до выполнения сценария.

## Подготовка

Прочитай [контракт кейса и данных](references/case-contract.md). Определи корень тестируемого проекта. При отсутствии нужного профиля создай env-привязки по разделу «Создание профиля по .env перед выполнением»: приложение — `config/profiles.json`, источники — `config/sources.json`. Сохраняй существующие настройки. Не выводи секреты и не угадывай неоднозначные соответствия.

Код находится в `scripts/`, установка и команды — в [runtime.md](references/runtime.md). Установи локальный пакет по этой инструкции, если он ещё не подключён. MCP должен быть доступен в клиенте отдельно. Отсутствие инструмента или обязательных данных блокирует зависимые действия; успешные результаты не имитируй.

## Полный цикл по кейсу или документации

1. Если требуется чтение источника, следуй [mcp-cases.md](references/mcp-cases.md): прочитай Jira/Wiki, сохрани кейс и источник. По документации сначала составь кейсы с проверяемыми ожиданиями; неизвестные требования оставь вопросами. Для локального готового кейса повторное извлечение не нужно.
2. Следуй [automation.md](references/automation.md): проверь реестр командой `playwright-qa plan` и существующие spec проекта. `run` — запусти актуальный тест; `create` — создай; `update` — сопоставь изменения и обнови; `blocked` — укажи причину.
3. Перед исследованием или исполнением UI явно открой тестовый стенд из env-профиля в отдельной вкладке/сессии, проверь фактический URL и продукт новым snapshot. Не выполняй шаги приложения на портале с описанием кейса. Для CLI-исследования прочитай официальный скилл `playwright-cli`, если он установлен; при его отсутствии используй установленный `--help` и честно укажи отсутствие инструкций.
4. При create/update напиши spec по [test-rules.md](references/test-rules.md) в структуре проекта (по умолчанию `e2e/`). Зарегистрируй проверенное соответствие кейсу и выполни `playwright-qa run`. Не регистрируй изменения лишь для обхода проверки ревизии.
5. Проверь код выхода, Markdown, скриншоты и результаты всех попыток. Разбери падения и классифицируй черновики багов. Форматы журнала и классификации — в [runtime-api.md](references/runtime-api.md).

Если MCP-работа делегирована доступному субагенту, получи путь к кейсу, профиль, подтверждённые наблюдения/локаторы и блокеры без секретов. Основной агент продолжает автоматизацию; завершение субагента не означает завершение задачи. При отсутствии субагентов выполни те же этапы последовательно.

## Другие режимы

- Чтение или составление кейсов: [mcp-cases.md](references/mcp-cases.md); закончи после сохранения описаний, если пользователь не просил прогон.
- Явный ручной прогон: [mcp-cases.md](references/mcp-cases.md); сохраняй пошаговый отчёт, spec не обязателен.
- Исследовательское тестирование: [exploratory.md](references/exploratory.md); сохраняй гипотезы, наблюдения, баги и новые кейсы. Автоматизация — если запрошена.
- Диагностика автотеста: [automation.md](references/automation.md) и [runtime-api.md](references/runtime-api.md).

## Критерий завершения

Для автоматизации сообщи ID кейса, путь к spec, результат runner, ссылки на отчёт и баги. Если spec не создан или runner не запускался, не называй задачу автоматизации завершённой: укажи, что осталось и почему. Не меняй продукт или ожидания ради зелёного прогона. Скриншоты каждого выполненного UI-шага обязательны либо нужна явная причина их отсутствия. Отчёт и папку изображений сохраняй в целевом проекте; секреты маскируй. Внешние баги автоматически не публикуй.
