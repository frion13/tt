# Запуск исполняемой части

Работай из корня целевого проекта с Node.js 22+ и npm. Если скопирован только QA-скилл, установи пакет прямо из его папки (путь к каталогу с SKILL.md):

```bash
npm install --save-dev --install-links /absolute/path/to/skill @playwright/test
npx --no-install playwright-qa init
npx --no-install playwright install chromium
```

Если package.json отсутствует, сначала выполни `npm init -y`. Путь с пробелами заключай в кавычки. Существующий совместимый @playwright/test сохрани: исключи его из команды установки. QA-скилл содержит весь runtime. Ключ `--install-links` нужен и для личных каталогов скиллов, чтобы зависимости разрешались из проекта. После обновления скилла повтори установку.

Альтернативная поставка — локальный архив, созданный `npm pack` в исходниках: `npm install --save-dev /path/to/playwright-qa-skills-0.2.0.tgz @playwright/test`. Публикация нашего пакета в npm не требуется.

`init` создаёт отсутствующие файлы, сохраняя существующие настройки. Полный архив также копирует навыки; поставка одного скилла не содержит соседние навыки и не устанавливает их. Если Playwright уже настроен, добавь `playwright-qa-skills/reporter` в список reporters и `use.ignoreHTTPSErrors: true`. MCP подключается отдельно в клиенте.

В spec используй `import {caseTest, expect} from 'playwright-qa-skills/test'`. Программный доступ к источникам экспортируется из `playwright-qa-skills/access`. Runtime находится в node_modules пакета, копирование runtime/ в проект не требуется. Для команд из другого каталога доступен `--project /path/to/project`.

В исходниках модули расположены в `runtime/`, внутри самостоятельного скилла — в `scripts/`; публичные импорты одинаковы. Форматы журнала и баг-репорта входят в скилл в `references/runtime-api.md`.

## Что исполняется

Маршрутизация агента хранится в `AGENTS.md`, создаваемом командой init. В нём определены задачи MCP, исследовательский режим, автоматизация, официальный CLI и баг-репорты. Это инструкции агенту, а не исполняемый диспетчер: он читает нужный SKILL.md и вызывает инструменты. Если инструкции команды уже существуют, init сохраняет их и сообщает, как включить отдельный `PLAYWRIGHT_QA.md`; автоматическое обнаружение зависит от клиента.

Форматы: [инструкции и навыки GitVerse](https://gitverse.ru/docs/ai/gigacode-on-gitverse/ai-workflow-scenarios).

| Файл | Назначение |
| --- | --- |
| `runtime/core.mjs` | Чтение кейса, `.env`, валидация данных, реестр и хеш ревизии |
| `runtime/access.mjs` | Отдельные профили источников, browser context, TLS-исключения |
| `runtime/test.mjs` | Обёртка caseTest/step, assertions через Playwright, скриншоты и журнал |
| `runtime/reporter.mjs` | Сбор результатов runner, попыток и Markdown-отчёта |
| `runtime/cli.mjs` | Команды plan/register/run/source/report |
| `runtime/import-report.mjs` | Импорт фактов MCP/исследования и копирование PNG |

GigaCode читает ссылку через MCP, исследует UI и пишет spec. Исполняемый модуль не преобразует произвольную страницу в правильный автотест самостоятельно. Он требует определённого кейса и проверяет/исполняет сохранённый код. Настоящих адресов, доступов источников кейсов и документации и продуктовых кейсов в проекте пока нет.

## Кейс и выбор существующего автотеста

Markdown содержит один JSON-блок `ttt-case` — это идентификатор формата, а не имя папки. Поля: `id`, `title`, `state` (ready/draft), `profile`, `data` (env-привязки), `steps` с уникальными целыми `id`, `action`, `expected`. Вне блока можно писать источник, предусловия и детали требований; изменение любой части Markdown меняет хеш.

```bash
npx --no-install playwright-qa plan test-cases/TC-123.md
npx --no-install playwright-qa register test-cases/TC-123.md e2e/TC-123.spec.mjs
npx --no-install playwright-qa run test-cases/TC-123.md
```

`plan` возвращает `create`, если привязки/spec нет; `update`, если кейс изменился; `run`, если ревизия совпадает; `blocked` для draft. После create/update агент пишет или проверяет spec, регистрирует его и запускает. `register` не проверяет семантическое соответствие и не означает, что тест прошёл. В новый проект реестр переносится пустым; регистрируются только его собственные кейсы.

Команда `qa run` возвращает 0 для успешного runner, 1 при падении, 2 при блокере/ошибке процесса и 3, если нужна работа над кейсом/spec. Результат flaky сохраняется отдельно от passed. `npx --no-install playwright test` запускает весь набор напрямую; этот путь не проверяет хеш реестра, но также создаёт отчёты. Каждый тест изолирован отдельным контекстом. Обёртка не добавляет retries автоматически.

## Данные и профили

Скопируй `.env.example` в `.env`, если своего `.env` ещё нет, и заполни только нужные переменные. Окружение процесса/CI имеет приоритет. Файл читается через Node `parseEnv`, без исполнения shell и подстановки `$VAR`.

`config/profiles.json` связывает имя профиля со стендом, продуктом, ролью и env-именами. `data` кейса дополняет привязки, но не может переопределить URL/креды профиля. Формат привязки — строка с env-именем или объект `{ "env": "NAME", "type": "number", "allowEmpty": false, "secret": true }`. Поддерживаются строка, number, boolean (`true`/`false`); пустая строка разрешается только явно. Обязательные поля проверяются до действий.

`init` создаёт пустой `config/sources.json`. Агент добавляет в него только нужные источники по env и контексту ссылки. Поддерживается любое число источников с произвольными именами; один портал может хранить и кейсы, и документацию. Уже существующие профили сохраняются.

Пример профиля для произвольного портала (это шаблон, а не обязательные имена):

```json
{
  "case-portal": {
    "auth": "password",
    "env": {
      "baseURL": "CASE_PORTAL_BASE_URL",
      "login": "CASE_PORTAL_LOGIN",
      "password": "CASE_PORTAL_PASSWORD"
    }
  }
}
```

Для публичного источника используй `auth: "anonymous"` и только привязку `baseURL`. `.env` может иметь любые имена переменных; примеры:

```dotenv
CASE_PORTAL_BASE_URL=https://cases.example.test
CASE_PORTAL_LOGIN=
CASE_PORTAL_PASSWORD=
DOCS_PORTAL_BASE_URL=https://docs.example.test
DOCS_PORTAL_LOGIN=
DOCS_PORTAL_PASSWORD=
```

Проверка профиля без раскрытия секретов: `npx --no-install playwright-qa source case-portal https://cases.example.test/browse/TC-1`. Команда проверяет origin и наличие env, но не открывает сайт. Для браузерного кода `resolveSource(root, name, target)` и `openSource(browser, profile, authenticate)` открывают отдельный контекст; `authenticate({page, login, password})` — callback для конкретной исследованной формы входа. Готового универсального входа в произвольные порталы не существует: версии, формы, SSO и MFA различаются. Пока поддерживаются профили password/anonymous; API token/SSO требуют отдельного адаптера. Пароли источников не используются для тестируемого продукта.

## SSL/TLS

Игнорирование ошибок сертификата включено для всех сайтов: `ignoreHTTPSErrors: true` в runtime и Playwright Test. Настройка распространяется на ресурсы и редиректы всех созданных тестовых контекстов. Отдельных env-флагов источников кейсов и документации/продукта больше нет.

Playwright CLI читает `.playwright/cli.config.json` с `browser.contextOptions.ignoreHTTPSErrors: true`. Для MCP в `config/playwright-mcp.example.json` добавлен `--ignore-https-errors`: перенеси этот аргумент в активную конфигурацию клиента и перезапусти MCP. Уже запущенные браузеры не перенастраиваются автоматически.

Если в существующей MCP-сессии осталось предупреждение, агент может нажать видимые «Дополнительные настройки → Перейти» для любого сайта без отдельного подтверждения. Если кнопки нет, нужно пересоздать сессию с нужным параметром. Настройка не отключает TLS для системных утилит или npm. Выбор профиля учётных данных и проверка origin источника сохраняются. Режим TLS записывается в отчёт.

## Написание теста и отчёты

Смотри минимальный spec в конце этого документа. `caseTest(file, callback)` передаёт `page`, `context`, проверенные `data`, `profile`, `step`. Каждый `step(id, operation, options)` выполняет действия и assertions, а operation возвращает наблюдаемый факт. Шаги должны соответствовать кейсу по порядку; недостающие шаги не превращаются в passed. На ошибке сохраняется снимок до закрытия context, ошибка пробрасывается runner. Данные приложения очищает `finally` самого теста; runtime закрывает браузерный контекст.

Отчёт — `reports/automation/<run-id>.md`, снимки — `<run-id>/screenshots/`, результаты — `summary.json`. Каждый retry сохраняется отдельно. Файл обновляется после шагов. При принудительном завершении процесса уже записанные артефакты остаются, но окончательный статус может быть running; CLI отмечает незавершившийся запуск. Для завершённых попыток не теряются failed/blocked/not_run/skipped. Код выхода runner и итог flaky записываются отдельно.

По умолчанию маскируются input/textarea, `[data-sensitive]` и известные значения секретов на странице. Для других чувствительных элементов передай `options.mask` (массив Playwright-локаторов). `options.noScreenshot` — непустая причина отсутствия снимка, например шаг без UI. Это не автоматическая гарантия отсутствия всех персональных данных: маски надо дополнить для конкретного интерфейса. Trace/video выключены по умолчанию. Отчёт и всю папку изображений передавай вместе.

## Импорт MCP/исследования

Сохрани наблюдения в JSON, а снятые через MCP PNG — рядом. Пример структуры (шаблон, не результат проверки):

```json
{
  "mode": "manual",
  "summary": { "status": "passed" },
  "records": [{
    "id": "TC-1", "profile": "stage-news-editor", "browser": "chromium",
    "status": "passed", "attempt": 1,
    "steps": [{ "id": 1, "action": "Открыть форму", "expected": "Форма видима",
      "actual": "Форма отображается", "status": "passed", "screenshot": "step-1.png" }]
  }]
}
```

`npx --no-install playwright-qa report evidence/journal.json` проверяет структуру и PNG, копирует изображения и создаёт `.md`. Для исследования mode — `exploratory`, допустимы статусы шагов `observation`/`question`. Без снимка требуется `screenshotError` с причиной. Импортёр не выполняет тест и не подтверждает введённый факт; маскирование изображения нужно выполнить при захвате. Снимки должны находиться внутри проекта. Можно добавить `context` со стендом/продуктом/ролью/env-привязками для отображения в отчёте.

## Баг-репорты

Упавший шаг автоматически создаёт отдельный Markdown-черновик в `reports/<mode>/<run-id>/bugs/BUG-<id>.md`: шаги до ошибки, ожидание и факт, профиль, env-имена, скриншоты и ссылка на отчёт. Черновик не означает подтверждённый баг продукта: агент определяет причину. Для blocked без выполненного упавшего шага файл не создаётся.

После диагностики сохрани `evidence/assessment.json`, например (это шаблон, не результат реальной проверки):

```json
{
  "id": "TC-123", "browser": "chromium", "attempt": 1,
  "kind": "product", "title": "Форма не сохраняет изменения",
  "reason": "Поведение противоречит требованию сохранения",
  "impact": "Пользователь теряет изменения", "severity": "major",
  "preconditions": "Роль editor, открыта форма существующей записи",
  "reproduction": "Повторено один раз с теми же предусловиями"
}
```

```bash
npx --no-install playwright-qa bug reports/automation/<run-id>/summary.json evidence/assessment.json
```

Команда обновляет тот же баг-репорт и сводный отчёт. `kind`: product/test/environment/requirements/unknown. Если повторной проверки не было, укажи это явно. Для импортируемого MCP-журнала классификацию можно передать в `record.defect`. Автоматического создания задачи во внешней системе нет. Файлы разных попыток сохраняются отдельно; это не означает разные баги.

## Проверки разработки

Следующие npm scripts выполняются из исходников пакета, не требуются в целевом проекте.

```bash
npm test
npm run test:browser
npm run skills:check
```

Первое проверяет env, реестр, профили источников, TLS-параметры и отчёты. Второе запускает Chromium: падение и retry, скриншоты, секреты, блокировку env и настоящий HTTPS с самоподписанным сертификатом. Для генерации тестового сертификата нужен `openssl`. Это проверки инфраструктуры, не тестирование источников кейсов и документации или вашего продукта.

## Минимальный формат кейса и spec

```ttt-case
{"id":"TC-123","title":"Форма входа","state":"ready","profile":"stage-editor","steps":[{"id":1,"action":"Открыть страницу входа","expected":"Поле логина видимо"}]}
```

Сохрани блок в Markdown-карточке. Имя profile должно существовать в config/profiles.json целевого проекта. Локатор и URL ниже — пример, их нужно подтвердить по настоящему интерфейсу:

```js
import {caseTest, expect} from 'playwright-qa-skills/test';
caseTest('test-cases/TC-123.md', async ({page, step}) => {
  await step(1, async () => {
    await page.goto('/login');
    await expect(page.getByLabel('Логин')).toBeVisible();
    return 'Поле логина отображается';
  });
});
```

При отсутствии нужного профиля агент создаёт `config/profiles.json` по именам переменных `.env` и контексту кейса (стенд, продукт, роль). Привязки источников кейсов и документации создаются отдельно в `config/sources.json`. Существующие настройки сохраняются, значения секретов в конфигурацию не копируются. При неоднозначности агент уточняет назначение переменных. Это правило скиллов; команда `init` по-прежнему создаёт пустой файл профилей.
