# Автотесты по описанным кейсам

## Входной контракт

Перед использованием источника или выполнением кейса проверь нужный профиль. Если его нет, составь привязки по `.env` и контексту по разделу «Создание профиля по .env перед выполнением» в [контракте](case-contract.md). Сохрани существующие настройки; неоднозначные соответствия уточни, значения секретов не раскрывай.

Сначала найди ранее описанный кейс в файле, сообщении или указанном источнике. Принимай существующий формат проекта, если в нём определены ID/идентификатор, предусловия, данные, шаги и ожидаемые результаты. Для нового формата используй [контракт](case-contract.md).

Разреши из кейса профиль выполнения: стенд, продукт, роль и точные env-имена URL, логина и пароля. Сохрани эту привязку в конфигурации/fixtures и итоговом Markdown. Если старый кейс не содержит привязки, дополни её из однозначного контекста запроса/проекта; иначе уточни выбор до запуска. Не используй общую учётную запись другого продукта/стенда как fallback.

Если кейс уже описан, не составляй его заново и не требуй повторного подтверждения. Если он доступен только по URL, извлеки его через раздел [работы с MCP](mcp-cases.md) и Playwright MCP. Если кейса нет, сначала подготовь его по предоставленным требованиям доступными средствами; при недостатке требований запроси недостающее. Не генерируй исполняемый тест с выдуманным ожиданием. Частично определённый набор автоматизируй в готовой части, указав непокрытые кейсы.

## Перед первым действием на сайте

Прочитай раздел «Переход от источника кейса к приложению» в [контракте](case-contract.md). После извлечения кейса явно открой стенд из env-привязки профиля приложения в отдельной вкладке/сессии, получи новый snapshot и проверь фактический URL и продукт. До этого не выполняй шаги кейса. Страница с описанием кейса не является стендом; при отсутствии URL приложения останови прогон как blocked.

## Исследование проекта и CLI

Для текущего проекта используй [исполняемый workflow](runtime.md): `qa plan` выбирает create/update/run, `qa register` связывает проверенный spec с ревизией кейса, `qa run` выполняет его. Готовый код находится внутри скилла в `scripts/`; его `package.json` позволяет установить runtime `playwright-qa-skills` из локальной папки по инструкции workflow, без отдельного архива. Для env и TLS переиспользуй модули runtime; не дублируй глобальные настройки SSL в тестах.

Для управления браузером используй официальный скилл `playwright-cli` из [microsoft/playwright-cli](https://github.com/microsoft/playwright-cli/tree/main/skills/playwright-cli), если он подключён. Сначала прочитай его установленный `SKILL.md`, затем только необходимые references. Раздел автоматизации `playwright-qa` задаёт процесс автоматизации, env-профили и Markdown-отчётность; официальный скилл задаёт работу с CLI. Сохраняй оба под разными именами, не заменяй один другим.

Официальная команда подключения после установки CLI — `playwright-cli install --skills`. Проверь фактический каталог установки и обнаружение в текущем клиенте; не предполагается, что установщик поддерживает папки всех клиентов. Для GigaCode при необходимости перенеси целиком каталог официального навыка с references в `.gigacode/skills/playwright-cli/`, сохранив содержимое. Если навык недоступен, явно отметь это и используй установленный `--help`; не утверждай, что официальный навык подключён только по наличию ссылки в инструкции.

1. Прочитай инструкции репозитория, package.json, lock-файл, конфигурацию Playwright, fixtures и соседние тесты. Сохрани язык, менеджер пакетов, структуру, настройки браузеров и принятый стиль. Для пустого JS/TS-проекта используй TypeScript и `@playwright/test`; если уже есть Python Playwright/pytest, следуй этому стеку и его runner-командам.
2. Проверь версии Node/runner и `playwright-cli --help`. Если отдельной CLI нет, проверь установленный Playwright и поддержку `npx --no-install playwright cli --help`; используй этот вариант только если команда поддерживается. Не заменяй пакет неожиданно загруженной через npx версией. Устанавливай зависимости локально по правилам проекта, сохраняй lock-файл и не обновляй чужие зависимости без необходимости.
3. Различай браузерную CLI (`playwright-cli` или поддерживаемый `playwright cli`) и runner (`playwright test`). Первая помогает наблюдать UI и получать локаторы, второй запускает сохранённые spec-файлы. Результат интерактивной CLI не является результатом автотеста.
4. Для UI-исследования через CLI открой заданный стенд, сними snapshot и проверь реальные элементы. Команды и аргументы бери из установленного `--help`. Обновляй snapshot после изменений; не переноси временные ссылки вида `e12` в spec-файл. При отсутствии CLI/доступа используй подтверждённые локаторы из кода или предыдущего исследования, явно отметив непроверенное. Не угадывай селекторы по названию кейса.

## Написание

Перед редактированием прочитай [правила автотестов](test-rules.md). Найди существующее покрытие и дополни его без дублей. Сохрани трассировку `ID кейса → файл и название теста → проверки ожиданий`. Разные варианты данных должны различаться в названиях тестов.

Подготовь данные и авторизацию через fixtures проекта, получая все входные тестовые данные из env по разделу «Тестовые данные через env» в [контракте](case-contract.md). Используй единый модуль чтения/валидации окружения, загружай `.env` до потребителей и передавай проверенные значения fixtures/тестам; для Node читай окружение процесса, для Python — окружение Python-процесса. Не хардкодь данные и не подставляй значения по умолчанию при отсутствии обязательной переменной. Добавляй необходимые имена и описание в `.env.example`. У каждого теста должны быть независимые предусловия и очистка даже после падения. Напиши действия и содержательные assertions для каждого обязательного ожидания. Не меняй требования, приложение или проверки ради зелёного прогона. При расхождении документации и UI сохрани исходное ожидание и сообщи о конфликте.

Обеспечь данные для обязательного Markdown-отчёта по [контракту](case-contract.md): ID и номер шага, действие, ожидание, наблюдаемый факт, статус и скриншот после каждого выполненного UI-шага. Переиспользуй reporter/helper проекта или добавь минимальную интеграцию для сбора шагов и формирования `.md` после каждого запуска, включая обычный запуск runner без агента. При ошибке сохраняй снимок до teardown и повторно выбрасывай исходную ошибку; сбой отчётности не должен её подменять. Одних скриншотов только при падении недостаточно. В существующий автотест без пошаговых артефактов добавь сбор доказательств без изменения проверяемого поведения. Не восстанавливай промежуточные факты из одного итогового скриншота и не подставляй ожидаемый результат в поле факта.

## Проверка и прогон

Команды ниже — для локального Node Playwright Test; адаптируй их к скриптам и менеджеру пакетов проекта. Замени пример пути реальным файлом. Сначала проверь установленный runner; `--no-install` не должен подменяться сетевой загрузкой.

```bash
npx --no-install playwright --version
npx --no-install playwright test tests/example.spec.ts --list
npx --no-install playwright test tests/example.spec.ts
```

- Проверь, что список тестов содержит все выбранные ID/варианты. Выполни принятые lint/typecheck для изменённой части, затем запусти созданные/изменённые тесты в настроенных проектах браузеров. `--list` проверяет обнаружение, но не исполнение.
- Дождись завершения процесса, сохрани точную команду, код выхода, окружение, число passed/failed/skipped/flaky и пути к отчётам. Пропущенный или успешный только после retry тест не выдавай за безусловный успех.
- Если отсутствуют URL, секреты, браузер или сервис, укажи `blocked`, выполненные проверки и точную причину. Не подставляй публичный сайт вместо стенда и не заявляй о пройденном тесте по чтению кода.
- Разбери падение по trace/ошибке: проблема теста, приложения, окружения или требований. Исправляй подтверждённую ошибку теста и повторяй затронутый прогон. Не увеличивай retries/таймауты вслепую и не зацикливайся: после двух исправлений без новой диагностической информации сохрани артефакты и блокер. Успех повторного запуска не отменяет исходную нестабильность.
- Расширяй прогон на связанное покрытие при изменении общих fixtures/config/helpers. Полный набор запускай по запросу или правилам проекта.

## Результат

При обнаруженном баге обязательно создай отдельный Markdown-баг-репорт по разделу «Отдельный баг-репорт» в [контракте](case-contract.md), приложи скриншоты и ссылку на прогон. После падения автотеста разбери созданный runtime черновик и отметь подтверждённую причину; не называй ошибку окружения багом продукта.

После каждого прогона сохрани таблицу покрытия и Markdown-отчёт в принятой папке, иначе `reports/automation/<run-id>.md`: ID, spec/test, каждый шаг с действием, ожиданием, фактом, статусом и отображаемым скриншотом, команда, код выхода, браузер, непокрытые пункты и причины. Сохрани изображения рядом с отчётом и проверь относительные ссылки по контракту. Для blocked/not_run укажи причины отсутствия снимков. Если runner завершился до формирования отчёта, собери `.md` из доступных фактов и отметь неизвестное; не выдавай неполный сбор за полноценный отчёт. В ответе дай путь к `.md` и папке изображений и фактический результат выполнения. Создание кода и успешное выполнение — отдельные результаты.
