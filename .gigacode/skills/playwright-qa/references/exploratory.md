# Исследовательское тестирование через MCP

Используй при запросах «исследуй продукт», «найди баги», «проведи exploratory testing» и для исследования области без готовых кейсов. Цикл сессии: изучить → сформулировать гипотезу → выполнить эксперимент → оценить наблюдение → выбрать следующий эксперимент. Не ограничивайся линейным проходом заранее составленного чек-листа.

## План сессии

1. Прочитай доступные требования и контекст запроса. Запиши цель, продукт, область исследования, исключения, роль и известные риски. Определи профиль env по [контракту](case-contract.md): стенд, продукт, роль и точные имена переменных URL/логина/пароля. Отсутствие готового кейса допустимо, неоднозначный стенд или доступ требуют уточнения.
2. Определи границу сессии: лимит пользователя, либо по умолчанию до 20 минут или 10 содержательных экспериментов, что наступит раньше. Запиши выбранный лимит и приоритеты в начале. По достижении лимита сохрани выводы и оставшиеся направления, не запускай бесконечный поиск.
3. Сохрани план в `reports/exploratory/<run-id>.md`, затем дополняй этот файл по ходу исследования. Применяй [правила шагов и скриншотов](case-contract.md): изображение каждого выполненного UI-шага, включая успешные, хранится в `<run-id>/screenshots/` рядом с отчётом и отображается по относительной ссылке.

## Исследование и эксперименты

- Начни с карты доступных функций и состояний в выбранной области. Проверь основной путь, затем направляй исследование по наблюдениям и рискам: границы ввода, пустые/невалидные значения, повторные действия, отмена, обновление/назад, сохранение состояния и ошибки. Проверяй роли только при наличии соответствующих разрешённых профилей. Не расширяй обычное исследование до нагрузочных атак или эксплуатации уязвимостей без запроса.
- Для каждого эксперимента назначь ID `EXP-001` и запиши гипотезу, начальное состояние, данные через env, последовательность действий и основание ожидаемого результата. Основанием может быть требование, явное сообщение интерфейса или обоснованное свойство продукта; укажи его источник. Неподтверждённое предположение так и назови.
- Все входные данные, включая негативные и граничные варианты, получай из env. Допускается генерация из документированных env-параметров/seed. Когда нужно новое значение, добавь его env-имя и назначение в `.env.example`, подготовь разрешённое несекретное значение в локальном `.env` без перезаписи чужих данных. Недостающие секреты не выдумывай. Продолжай независимые эксперименты при блокировке одного.
- Выполняй действия через реальные MCP-инструменты, обновляй snapshot после изменений. Разделяй фактическое наблюдение и оценку: неожиданное поведение ещё не доказывает дефект. При отсутствии основания для ожидания сохрани наблюдение и открытый вопрос без статуса passed/failed.
- После эксперимента решай, что проверить дальше по новой информации. Отмечай связь между экспериментами, но явно восстанавливай нужные предусловия; не считай неизвестное состояние результатом исправного setup.
- Сохраняй шаги, снимки и ошибки до cleanup. Не фиксируй секреты на скриншотах, в логах или Markdown. Останавливай действия за пределами разрешённого стенда/операций и фиксируй границу исследования.

## Находки и воспроизведение

Различай: подтверждённый дефект, подозрение, вопрос к требованиям и улучшение удобства. Для предполагаемого дефекта попробуй минимальный повтор из известного начального состояния в пределах оставшегося лимита и разрешённых действий. Если повтор не выполнен или не воспроизвёлся, сохрани исходные доказательства и явно укажи это; не стирай находку и не утверждай воспроизводимость.

Для подтверждённого дефекта сохрани отдельный Markdown-баг-репорт по разделу «Отдельный баг-репорт» в [контракте](case-contract.md) и добавь ссылку в журнал исследования. Для находки укажи ID `FIND-001`, связанный эксперимент, профиль, шаги воспроизведения, env-имена данных, ожидание с основанием, факт, влияние, скриншоты и результат повторной проверки. Не публикуй дефекты во внешней системе без запроса.

Для полезных воспроизводимых сценариев с определёнными ожиданиями создай карточки `test-cases/<ID>.md` по контракту, связывая их с экспериментами/находками. Это относится и к успешным сценариям, пригодным для регрессии. Не превращай каждое случайное действие в отдельный кейс. Неопределённые ожидания оставляй `draft` с вопросами.

Если пользователь запросил также автоматизацию, передай ready-кейсы в `playwright-qa`: найди существующее покрытие и автоматизируй недостающее. Сам запрос исследования не требует автоматически писать все автотесты.

## Итоговый Markdown

Отчёт содержит план и фактическую длительность, выбранный профиль и env-имена, журнал экспериментов со всеми шагами и скриншотами, находки, созданные кейсы, очистку, покрытые/неисследованные области и следующие приоритеты. Для каждой проверки с известным ожиданием используй статусы контракта; для открытого исследования отдельно укажи исход `наблюдение` или `вопрос`, не включай его в число passed. Отметь достижение лимита или другую причину завершения. Отсутствие найденных дефектов означает только результат исследованной области, а не полную проверку продукта.

Перед завершением проверь относительные ссылки и наличие изображений. В ответе дай путь к `.md`, папке скриншотов и созданным карточкам, перечисли основные находки и ограничения охвата.
