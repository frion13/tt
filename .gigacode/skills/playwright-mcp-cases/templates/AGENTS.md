# Выбор скиллов для тестирования

Эти правила относятся к задачам тестирования текущего проекта. Для других задач не подключай тестовые скиллы автоматически. Учитывай явный запрос пользователя и инструкции репозитория. Корень проекта определяй по текущему workspace; не используй пути или название папки из примеров и прошлых сессий.

## Маршрутизация

| Запрос пользователя | Скилл | Результат |
| --- | --- | --- |
| Прочитать кейс из Jira, разобрать Wiki, составить кейсы по требованиям | `playwright-mcp-cases` | Карточки Markdown с источниками, профилем и ожиданиями |
| Пройти сценарий через браузер, без создания автотеста | `playwright-mcp-cases` | Фактический пошаговый прогон и Markdown со скриншотами |
| Исследовать продукт, найти баги без готового кейса | `playwright-mcp-cases` и его `references/exploratory.md` | Журнал экспериментов, находки и новые кейсы |
| Создать/обновить автотест, запустить уже описанный кейс через runner | `playwright-cli-tests` | Поиск покрытия, spec, запуск и отчёт |
| Изучить локаторы или выполнить действия через CLI при автоматизации | `playwright-cli` вместе с `playwright-cli-tests` | Подтверждённые элементы и команды браузера |
| Только браузерная операция через CLI, snapshot или скриншот | `playwright-cli` | Запрошенный браузерный артефакт |
| Разобрать падение автотеста, оформить баг | `playwright-cli-tests`; MCP-скилл при необходимости воспроизведения через MCP | Причина падения и отдельный Markdown-баг-репорт |
| Оформить баг по наблюдению MCP/исследования | `playwright-mcp-cases` | Отдельный Markdown-баг-репорт и ссылка в журнале |

Перед работой прочитай SKILL.md выбранного навыка и только нужные references. Найди его через механизм клиента или в `.gigacode/skills/<name>/`. При отсутствии навыка или инструмента сообщи о конкретном блокере, не имитируй его выполнение. Наличие файла не означает подключённый MCP или установленный CLI.

## Ссылка на кейс: полный цикл

Если пользователь просит выполнить/автоматизировать кейс по ссылке, используй последовательность:

1. `playwright-mcp-cases`: прочитай источник, используя отдельный профиль Jira/Wiki из env. Сохрани кейс в Markdown с исходным ID, источником, предусловиями, шагами, ожиданиями и профилем приложения. URL документации не является URL стенда.
2. `playwright-cli-tests`: при установленном runtime выполни `npx --no-install playwright-qa plan <case.md>` из корня целевого проекта.
3. По ответу `plan`: `run` — запускай существующий тест; `create` — исследуй UI, создай spec; `update` — сопоставь изменение кейса с кодом и обнови spec; `blocked` — уточни неопределённые требования. Не регистрируй изменённый кейс лишь для обхода проверки его ревизии.
4. Для исследования через CLI прочитай официальный `playwright-cli`. Для нового/обновлённого spec после проверки соответствия выполни `playwright-qa register <case.md> <spec>`, затем `playwright-qa run <case.md>` через локальную команду или `npx --no-install`.
5. Дождись завершения, проверь Markdown-отчёт, скриншоты и код выхода. При падении разбери причину, обнови созданный черновик баг-репорта; не объявляй каждое падение багом продукта.

Для запроса «только прочитай/составь» остановись после сохранения кейсов. Для явного ручного прогона используй MCP и не создавай spec без запроса. Для исследования отсутствие готового кейса не блокер. Одна ссылка без действия: учти уже заданную задачу; если намерение всё ещё неизвестно, прочитай доступный источник и уточни, нужен разбор, прогон или автоматизация, прежде чем выполнять сценарий.

## Общие условия

- Перед доступом к источнику или прогоном проверь нужный профиль. При отсутствии создай его по именам переменных `.env` и однозначному контексту кейса/проекта: приложение — `config/profiles.json`, Jira/Wiki — `config/sources.json`. Записывай только env-имена, сохраняй существующие профили и не выводи секреты. Неоднозначности уточняй по правилу «Создание профиля по .env перед выполнением» в контракте выбранного QA-скилла.
- Стенд, продукт, роль и точные env-имена URL/логина/пароля должны быть определены до действий. Jira/Wiki и тестируемое приложение используют разные профили. Недостающий доступ блокирует только зависимую часть задачи.
- Все входные данные берутся из env/локального `.env`; секреты не записываются в кейсы, отчёты и скриншоты. Ошибки SSL/TLS игнорируются для всех сайтов в тестовых браузерах по настройкам пакета. Учётные данные передавай только выбранному источнику/продукту.
- После прогона сохраняй `.md` с шагами, ожиданием, фактом, статусами и отображаемыми скриншотами. При подтверждённом дефекте сохраняй отдельный `.md`-баг-репорт; в Jira его автоматически не публикуй.
- Каждый QA-скилл содержит `scripts/` и `package.json`: при отсутствии runtime установи его из локальной папки выбранного скилла по `references/runtime.md`, без поиска отдельного архива. Код выполнения предоставляет установленный `playwright-qa-skills`; импорт теста — `playwright-qa-skills/test`, reporter — `playwright-qa-skills/reporter`. Если runtime не установлен, следуй `references/runtime.md` выбранного скилла, сохраняя существующий test harness. Не предполагается, что пакет опубликован в публичном npm.
- Не меняй продукт, ожидания или assertions ради зелёного прогона. Различай passed/failed/blocked/not_run и flaky. В ответе давай ссылки на фактически созданные файлы и честно указывай непроверенные части.

## Примеры выбора

- «Прочитай кейс из Jira» → MCP, Markdown-карточка, без запуска сценария.
- «Автоматизируй и пройди кейс по ссылке» → MCP → поиск автотеста → CLI при необходимости → runner → отчёт/баг.
- «Исследуй оформление заказа 20 минут» → MCP, исследовательский режим → журнал → баги/кейсы; автотесты только при запросе.
- «Запусти уже готовый TC-123» → скилл автотестов → проверка реестра → runner; повторное чтение Jira нужно только при запросе актуализации или недостающих данных.
